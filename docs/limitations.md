# 已知限制与威胁边界

本文档坦诚记录 PasswordNotebook 目前的技术边界、已知限制以及客观存在的安全对抗边界，便于使用者建立清晰的威胁模型预期。

---

## 1. 内存残留与取证边界

在现代操作系统和高级语言运行环境下，敏感数据在内存中的绝对「零残留」是不可能完全保证的。PasswordNotebook 通过 Rust 的 `zeroize::Zeroizing` 对核心敏感数据（DEK、派生密钥、整库 JSON 明文、条目密码与 API 密钥、剪贴板中转缓冲与读取比对的副本、恢复码）进行了离开作用域主动覆写清零，但依然存在以下**不可逾越的客观边界**：

1. **Win32 原生输入控件缓冲**：
   - 界面上的密码输入框（Win32 `EDIT` 控件）由 Windows 系统模块（`user32.dll`）内部管理其文本内存。
   - 虽然程序读取输入时使用了安全宽字符容器，但 Windows 控件内部私有堆内存的生存周期不受应用程序直接掌控，在窗口或控件被彻底销毁前，该控件内存无法被本进程主动擦除。
2. **JSON 序列化与反序列化瞬态副本**：
   - 保险库采用 `serde_json` 组织结构化明文数据。在解析 JSON 字符串为内存结构体、或将结构体序列化为密文载荷的过程中，底层分配器会产生瞬态的堆内存字符串与碎片副本。这些短命副本在被操作系统重新分配或覆写前，可能在堆空闲列表中短暂停留。
3. **威胁评估结论**：
   - **内存清零的核心价值是抬高取证门槛、大幅缩短敏感数据的暴露时间窗口，而不是彻底免疫物理取证**。
   - 拥有本地 Administrator/SYSTEM 权限、能够实施内核级内存倾倒（Crash Dump / Memory Forensics）、或能够直接读取磁盘休眠文件（`hiberfil.sys`）的攻击者，在理论上仍可能在特定时间窗口内恢复出部分明文片段。若运行环境本身已被完全攻陷，任何用户态密码管理器均无法独善其身。

## 2. 本机免密缓存（Quick Unlock）的信任边界

本机免密解锁利用了 Windows 提供的 DPAPI 数据保护接口，其安全边界取决于本机 Windows 账户：

1. **绑定主体为 Windows 账户而非开机密码**：
   - DPAPI 凭据绑定的是当前已登录的 **Windows 账户上下文**。
   - **修改 Windows 账户的登录密码并不会让 DPAPI 缓存失效**（Windows 内部主密钥会自动平滑迁移）。
   - 若要作废免密缓存，请在主界面点击「锁定」按钮，或在设置界面中关闭「记住解锁状态」。
2. **同会话进程边界**：
   - 在同一个已登录的 Windows 用户桌面会话中，以相同用户权限运行的恶意软件理论上同样具备调用 `CryptUnprotectData` 的系统权限。
   - **防御建议**：在公共电脑或多用户共享电脑上，建议在设置中勾选**「使用 Windows Hello 验证」**（从锁定/锁屏恢复进入时强制要求指纹/面容/PIN 物理在场授权），或者直接**关闭「记住解锁状态」**。
3. **离线/未运行期间的锁屏感知**：
   - 锁屏即时清除机制依赖程序后台消息循环捕获会话变更通知。若在**程序未处于运行状态**时计算机发生了锁屏或切换用户，程序在下次冷启动时无法追溯此前的锁屏事件。
4. **缓存写入失败的如实告知**：
   - 缓存文件写在 `%LOCALAPPDATA%\PasswordNotebook\quickunlock.dat`。若该目录被安全策略、权限或磁盘状态拒绝写入，免密解锁**不会生效**（下次仍需输入登录密码），密码本本身的功能不受影响。
   - 设置界面会检查缓存是否真的存在：不可用时在状态栏明确提示，勾选「记住解锁状态」后保存失败也会把原因（含系统错误码）显示出来，不会出现「界面显示已开启、实际从未生效」的情况。

## 3. 搜索能力说明

- **子串包含匹配**：
  - 主界面的搜索框采用**多字段大小写不敏感子串匹配**（检查输入文本是否为标题、用户名、网址、API 端点、分类、标签或备注的子串；密码与 API 密钥不参与搜索）。
  - **不是**拼音搜索，**不是**编辑距离模糊纠错（Fuzzy / Levenshtein），亦不包含全文分词倒排索引。输入关键词时需确保包含连续的目标字符片段。
- **结果排序是启发式的**：
  - 命中之后按匹配质量排：标题完全相同 > 标题前缀命中 > 标题包含 > 用户名 > 网址 / API 端点 > 标签 > 分类 > 备注。
  - 收藏条目永远排在最前（收藏是用户显式表达的「常用」，不被一次临时搜索压下去）；同分时再按用户选择的排序方式（更新时间 / 标题 / 分类）决定先后。
  - 这套规则是固定权重，没有学习或个性化；权重表见 `src/search.rs`。

## 4. 架构与功能限制

- **自创文件格式与生态隔离**：
  - 保险库格式 `.pkk` 为自研单文件加密格式（详见 [docs/security.md](security.md)）。
  - 目前暂无第三方工具支持直接解析，需要通过本程序内置的 CSV / JSON 导入导出进行迁移（见第 5 节）。
- **KDF 参数初始化固化**：
  - Argon2id 的计算参数（64 MiB 内存、3 次迭代、4 路并行）在创建保险库时固化写入文件头明文区，当前版本未在设置界面中提供动态调参功能。
- **单数据库绑定**：
  - 程序定位为轻量便携工具，默认单一绑定 exe 所在目录的 `data.pkk`（若目录不可写则自动回退至用户「文档」目录），不提供多库切换、多账本并行管理。
- **旧版本打开新库会丢掉 API 密钥/端点**：
  - 0.3.0 起条目新增 `api_key` 与 `api_endpoint` 两个字段。0.2.x 及更早版本读库时会忽略这两个未知字段；若用旧版本打开 0.3.0 写出的库并做任何保存，**新字段会被静默抹掉**（其余数据不受影响）。
  - 升级后请只用 0.3.0 及以上版本打开写有这两个字段的库；在旧版本上操作过后，需要重新补填。
  - 反向的次要影响：用 0.2.x 导入 0.3.0 导出的 CSV 时，旧版本认不出 9 列表头，公式防护前缀不会被还原（以 `=` `+` `-` `@` 开头的值可能多出一个前导单引号），`ApiKey` / `ApiEndpoint` 两列也会被忽略；0.2.x 自己导出的旧文件不受影响。
- **整库读写,不支持多机同步**:
  - 解锁时把整个 `.pkk` 读进内存,之后任何一次改动(包括只改一个「收藏」标记)都会把**整个库**重新序列化、重新加密、整份写回(`vault.rs` 的 `save()` → `vaultfile.rs` 的 `write_atomic()`)。没有条目级存储、没有索引、也没有任何「磁盘上的库是否被别人改过」的检测。
- **解锁期间库文件被本程序占用**:
  - 解锁后,程序会以「只共享读取」的方式持有 `data.pkk` 的句柄:外部程序(含资源管理器)对它**删除、改名、覆盖写都会被系统拒绝**(「文件正在被使用」),只读访问(备份软件、杀毒扫描)不受影响。锁定或退出后占用释放。
  - 设计动机:防止库文件在打开期间被外部改动/删除/撤销(Ctrl+Z)后与内存态静默分叉——极端情况下(重生成恢复码后文件被顶回旧版)会导致「新凭据打不开、旧凭据已销毁」。
  - **边界**:占用只能挡住「打开期间」的外部操作。程序未运行时的删除、替换、回滚(含资源管理器撤销、同步客户端版本回滚、用旧备份整份顶替)依然成立——口令加密的单文件格式对此无解(等价于加密压缩包的旧副本永远可用旧密码打开),重要凭据轮换后建议另外导出一份 JSON 备份。
  - 每次写盘(临时文件 + 原子改名)前会短暂释放占用、写完立刻重新占用,窗口只有几毫秒。
  - 因此**同一个库文件不要被两台及以上设备同时使用**：后保存的那份会整份覆盖前一份，另一台的改动不会合并、不会报错、直接消失。程序全程只在解锁时读一次文件，解锁期间不会重新加载。
  - 放在 OneDrive / Dropbox 这类同步目录里时还要额外注意：同步客户端产生的冲突副本（如 `data-<机器名>.pkk`）**不会被本程序读取**（文件名是写死的 `data.pkk`）；在两台机器上改主密码还会互相回退（密钥代数 `key_generation` 记在文件头里，会被整份覆盖）。
  - 现阶段的建议是「同一时间只在一台设备上打开，用完立即锁定并等待同步完成」，重要改动后另外导出一份 JSON（见第 5 节）作为可回导的增量备份。同步客户端的版本历史是最后一道兜底。
  - 真要支持多机并发，需要的是条目级版本与合并协议（现有条目已带稳定 `id`、`updated` 时间戳与删除墓碑，具备实现基础），而不是单文件整存整取的增量写入 —— 那属于另一套存储模型。
- **分类页签溢出会被裁掉**：
  - 主界面顶部的分类页签条是自绘的单行控件，只排一行；分类多到超出可用宽度时，右侧放不下的页签会被直接裁掉（不换行、不滚动）。
  - 「只看收藏」开关特意独立放在页签条之外，不占用这一行。
  - 规避办法：分类名取短一些，或用搜索框按分类、标签关键字查找（搜索与页签是叠加关系）。
- **弹窗尺寸固定，工作区逻辑高度装不下时会裁掉底部**：
  - 各对话框使用固定尺寸（条目编辑 800×500、设置 380×730 等），尺寸按**含标题栏/边框的窗口高度**计算；窗口位置会夹进显示器工作区，但工作区本身比弹窗还矮时，底部按钮会落到屏幕外（可 Tab 聚焦后用空格触发，键盘操作不受影响）。
  - 常见触发组合：1366×768 @150% 这类逻辑空间很小的配置（工作区逻辑高不足约 500）；1080p / 1440p @175% 下条目编辑窗口（500）可以完整放下。
- **单语言界面**：
  - 目前界面文字全部为简体中文，尚未抽取资源字典进行多语言国际化（i18n）。
- **单条改动是「先改内存再落盘」**：
  - `add_entry` / `update_entry` / `move_to_bin` / `restore_from_bin` / `purge` / `empty_bin` / `toggle_favorite` / 分类标签增删改 / `update_settings` 都是先改内存中的文档、再调 `save()`。写盘失败（磁盘满、目录权限被杀软拦截、同步冲突）时，磁盘没变而内存已经变了。
  - 这些改动**不丢数据**：只要之后任何一次 `save()` 成功，就会把它们一并写出。为此程序用一个「有改动未落盘」标记（`VaultService::has_unsaved_changes`）如实记录该状态：状态栏持续显示警告，「保存失败」弹窗会说明改动仍在内存里、只是没写进文件。
  - **锁定与退出会丢掉这些改动**（内存文档随 `lock()` 一起消失）。为此：手动点「锁定」或关闭程序时会先尝试补一次保存，失败才询问是否仍要继续；空闲自动锁定与锁屏属于系统事件、不能弹窗，那两条路径只靠状态栏上的常驻警告提前告知。
  - 批量导入（`import_entries`）不在此列：它在**文档副本**上算好、写盘成功后才提交，失败时内存与磁盘都不受影响。
  - 只有重包密钥槽的三条路径（改主密码 / 重设主密码 / 重生成恢复码）会直接落盘 `file.payload` 而不经过 `save()`；它们在动手前会先把待写内容落盘，避免把内存里攒着的改动悄悄覆盖掉。

## 5. 导入 / 导出的边界

- **导出文件是明文**：
  - 导出到 CSV / JSON 的文件不经过任何加密（也不应该加密：它的用途就是交给别的工具读取）。
  - 是否把**密码与 API 密钥**写进文件，由导出时显式勾选决定；不勾选时文件里只有标题、用户名、网址、API 端点、分类、标签与备注，可以放心贴在工单或共享文档里。
  - 文件一旦落盘即等同于一份明文清单。普通删除不保证磁盘扇区被覆写，请尽快导入目标密码管理器并自行处理该文件。
- **不被导出的内容**：回收站中的条目、库内设置（本机免密解锁、自动锁定、剪贴板等待时间等）。
- **CSV 公式注入防护**：
  - 以 `=` `+` `-` `@` 或单引号开头的单元格会被加上一个前导单引号，防止在 Excel 中打开时被当作公式执行（OWASP 建议的做法）。
  - 导入时**只对本程序自己导出的文件**（判据：带 BOM，且表头是本程序新旧两代表头之一、顺序一致 —— 0.2.x 的 7 列与 0.3.0 起的 9 列，含/不含凭据均可）还原该前缀，因此自身往返（含经 Excel 另存为「CSV UTF-8」再导回）不受影响；用别的工具打开时可能看到多出来的单引号。
  - 第三方 CSV 不做还原：那个前缀是带内转义，而单引号本身可能就是数据（别人家导出里 `'=x` 是一个以单引号开头的真实密码），无条件去前缀会静默吃掉一个字符。详见 [docs/security.md](security.md) 第 6 节第 3 条。
- **编码只支持 UTF-8**：
  - 导入接受带或不带 BOM 的 UTF-8。中文 Windows 上 Excel 默认另存为 GBK/ANSI，这类文件会被明确拒绝并提示改用「CSV UTF-8（逗号分隔）」重新保存，而不是导入一堆乱码。
- **导入有体积与条数上限**：
  - 单次导入上限为 64 MB / 100000 条（`MAX_IMPORT_BYTES` / `MAX_IMPORT_ENTRIES`，见 `export_import.rs`）。两者互补：体积够小也能塞下海量行（含空行），而每行都要展开成 `Vec<String>`、每条最终还要变成一个 `Entry`，开销远超文件本身。
  - 体积上限在**读取之前**按文件元数据判断，超限文件一个字节都不会进内存；`parse()` 自身也再判一次（自检等调用方已经读进内存时仍能拒绝）。
  - 条数上限同时落在「展开记录」（`parse_csv_records`，导入链路上最占内存的一步）与最终 `Entry` 两处，因此即使调用方绕过文件路径直接调 `parse()`，也不会被超大输入拖垮。
  - **空行同样计入条数上限**：否则一个 64 MB 的纯换行文件能撑出六千多万个 `Vec<String>`，而它们一条条目都变不出来 —— 体积上限刚好放这种文件过关，光靠它挡不住。
  - 上限留了两个数量级余量，个人密码管理器实际用到的导出文件通常在几百 KB。若确实需要突破，请按批次拆分文件导入。
  - 导入期间仍需给库复制一份副本（见 [docs/security.md](security.md) 第 6 节第 6 条），所以内存占用约为「库 + 导入内容 + 序列化缓冲」之和。release 构建使用 `panic = "abort"`，极端情况下内存耗尽时进程直接退出，不会有提示。
- **字段映射是启发式的**：
  - 导入按表头别名识别列（标题 / 用户名 / 密码 / 网址 / API 密钥 / API 端点 / 分类 / 标签 / 收藏 / 备注及其常见英文名）。无法识别的列会被忽略（例如 Bitwarden 的 `totp`、`fields`），当前版本不导入 TOTP 一次性密码、附件与自定义字段。
  - CSV 中的标签以 `;` 或 `|` 分隔。收藏列接受 `1` / `0` / `true` / `yes` / `是` 等写法（Bitwarden 的 `favorite`、LastPass 的 `fav` 都能识别）。
- **去重规则**：
  - 按「标题 + 用户名」判断重复（忽略大小写与首尾空白）；两者都为空时退化为网址。
  - 覆盖策略下，文件中为空的密码与 API 密钥**不会**清空库内已有的对应值；收藏状态同理，只「置上」不清除。API 端点与网址同级：无条件覆盖（文件里为空就会清掉原值）。
  - 三个身份字段（标题 / 用户名 / 网址）都为空的条目**无法去重**（例如只有备注、密码或 API 密钥/端点的行）：同一份文件重复导入时，「跳过 / 覆盖」都匹配不上，会一条条变成新条目。
- **收藏状态与文件格式**：
  - JSON 导出/导入会完整保留收藏状态；CSV 默认 9 列（0.3.0 起在 `Url` 后多了 `ApiKey`、`ApiEndpoint`），**不承载收藏**，因此 CSV 往返会丢掉收藏标记。取消勾选「包含明文密码与 API 密钥」时导出的是 7 列（少掉 `Password` 与 `ApiKey`）。要连收藏一起备份，请用 JSON 或加密的 `.pkk` 副本。
  - 因为「不含收藏信息」与「明确未收藏」在 CSV 里无法区分，覆盖导入时不会取消已有收藏。代价：无法通过导入来取消收藏，请在主列表的右键菜单里操作。
- **不支持**：KeePass `.kdbx`、1Password `.1pux`、加密的导出文件等二进制格式。
