# PasswordNotebook 代码审核报告

- **仓库**:https://github.com/Bikakko/passwordnotebook(审核时点 HEAD:`1bddec3`)
- **技术栈**:Rust(edition 2024)+ 原生 Win32,可移植核心库 + Windows 界面层
- **审核方式**:静态阅读(本机无 Rust 工具链,未做编译/测试验证)
- **结论先行**:**整体质量很高,没有发现可直接导致机密泄露的高危缺陷**。加密方案标准且实现谨慎,威胁模型文档的坦诚度罕见。发现的问题中,后果最重的是「库文件解锁期间无外部变更检测」——它本身不泄露数据,但在特定操作链下可导致**库永久打不开**(数据丢失级),列为 M1。

---

## 一、总体评价

这不像一份业余作品,更像被多轮审查打磨过的代码:

- **加密架构正确**:AES-256-GCM(AEAD)+ Argon2id(64 MiB / 3 / 4),DEK 与 KEK 分离,双密钥槽(主密码 + 恢复码)对称设计,三套独立 AAD 让改密/重生成恢复码不必动载荷(`src/header.rs`、`src/vault.rs`)。
- **落盘可靠性做得很细**:临时文件 → `sync_all` → `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 的原子写,写盘失败时载荷与 nonce **成对回滚**,dirty 标记如实反映「内存超前于磁盘」(`src/vaultfile.rs:88`、`src/vault.rs:828`)。
- **内存卫生到位**:DEK/KEK/明文缓冲/条目密码/恢复码/剪贴板副本全部 `Zeroizing`,DPAPI 解出的明文缓冲在 `LocalFree` 前手动清零(`src/win/dpapi.rs:209`)——这个细节绝大多数项目会漏。
- **防御性解析**:坏头部的 KDF 参数上界、载荷长度校验、导入体积/条数双上限、URL 协议白名单、CSV 公式注入防护且只对自家文件还原前缀——都是踩过坑才会写的代码。
- **注释即文档**:大量「为什么这样做」的记录(失败模式、实测现象、权衡),`docs/limitations.md` 对威胁边界的坦白(Win32 控件缓冲不可清零、DPAPI 绑定账户而非密码)值得点赞。

## 二、问题清单

### 🔴 高优先级

**无。** 没有发现可直接导致机密泄露、认证绕过的问题。

### 🟡 中优先级

#### M1. 解锁期间对磁盘上的 .pkk 既不锁定也不校验,外部删除/替换/撤销可造成静默回滚,极端操作链下库永久打不开
`src/vault.rs:232-243`(save)、`src/vault.rs:291-341`(rewrite_slot)、`src/vaultfile.rs:88-113`(write_atomic)

**机制确认**:库文件只在解锁时 `std::fs::read` 一次,之后不再持有句柄、不加共享锁、保存前也不比对磁盘状态——`write_atomic` 是无条件的「临时文件 + 改名顶替」。`docs/limitations.md` 承认了多设备场景「没有任何磁盘上的库是否被别人改过的检测」,但**同一台机器上**的以下路径没有覆盖:

- **小问题(替换 + Ctrl+Z)**:库打开期间,磁盘上的 `data.pkk` 可被外部替换;资源管理器对「替换」的撤销(Ctrl+Z)能把旧文件复活。程序对此完全无感,内存态与磁盘态静默分叉,下一次保存整份覆盖,撤销产生的新旧交替没有任何提示。
- **大问题(删除 → 修改 → Ctrl+Z 还原)**:打开密码本 → 删除 `data.pkk` → 在软件里修改内容(任何改动都会触发 `write_atomic` 重新**生成**一个 `data.pkk`)→ 关闭软件 → 资源管理器里 Ctrl+Z 撤销删除,旧的 `data.pkk` 与新生成的文件撞名,确认替换后**旧库顶掉新库**。
- **灾难链(凭据轮换 + 回滚)**:把上面「修改内容」具体化为**重新生成恢复码**——用户抄下新恢复码、销毁旧恢复码(甚至可能同时重设了主密码)。此时新凭据只存在于新文件的密钥槽里;Ctrl+Z 一回滚,磁盘上变回旧库:旧主密码槽 + 旧恢复码槽。用户手里的新恢复码对旧库无效,旧恢复码已销毁——若主密码也恰好记不住,**库永久打不开,无药可救**。
- **恶意变体(回滚攻击)**:能写该文件的攻击者可以用此前捕获的旧版 `.pkk` 替换当前文件。`key_generation` 刻意不进任何 AAD(`header.rs:220` 的测试明确了这一取舍),载荷内也没有单调版本计数,因此旧主密码/旧恢复码在旧文件上重新生效——「改密码让泄露的旧密码作废」这个安全预期,对「文件被替换」不成立。口令加密文件格式天然无法自带防回滚(没有可信存储放单调计数),但**本机其实有可信位置可用**(见建议 3)。

**修复方案与决策记录**:评审后作者选择了**占用锁**方案并已落地实现(见下方「已实现的修复」),放弃了指纹校验与单调计数器两条检测路线。理由成立:

- 跨重启/程序未运行时的回滚本来就堵不死——口令加密单文件格式没有可信位置存单调计数,旧副本永远可用旧凭据打开(等价于加密 RAR 的旧副本);作者明确接受这一边界。
- 占用锁把「打开期间」这个唯一可控的窗口管起来,实现成本远低于检测方案,且不引入新的交互(无需弹窗)。

**已实现的修复**(本次评审分支):

1. 新增 `src/filelock.rs`:`FileLock` 以「打开句柄 + 只共享 `FILE_SHARE_READ`」占用 `data.pkk` —— 外部进程(含资源管理器)对它删除/改名/覆盖写一律得到「文件正在被使用」;备份软件、杀毒扫描等只读访问不受影响(内容为密文,可读无妨;连读都要禁可把 `share_mode` 改为 `0`)。含 Windows 专项单测(占锁挡写/挡删/放行读、放锁恢复)。
2. `VaultService` 增加 `lock_handle` 字段:`install()` 先占锁再宣布解锁(占不到就报错不开,不占半个便宜);`lock()` 随密钥一起释放占用。
3. 写盘统一走 `write_without_lock()`:放锁 → 临时文件 + 原子改名 → **无论成败**重新占锁。必须放锁的原因:原子改名顶替目标时目标不能被「未共享删除」的句柄占着,自己这把也算。`save()` / `rewrite_slot()` / `import_entries` 三条落盘路径全部接入。
4. `docs/limitations.md` 同步补充该行为与边界(占用只管「打开期间」;未运行时的删除/替换/回滚仍成立,凭据轮换后建议另存 JSON 备份)。
5. 残留窗口:放锁到重新占锁之间有几毫秒空档,外部操作恰好落在这个窗口仍可能成功——实际可利用性极低,接受。
6. 多实例并发已由既有的单实例互斥锁(`win/mod.rs` 的 `PasswordNotebook.SingleInstance.v1`)覆盖,无需额外处理。

#### M2. 复制密码未排除 Windows 剪贴板历史记录与云剪贴板
`src/win/clipboard.rs:16-63`

`set_text` 只放了 `CF_UNICODETEXT`。Windows 10 1809+ 的**剪贴板历史(Win+V)和云剪贴板同步**会在后台留存密码副本——程序 20 秒后「自动清空剪贴板」只能清当前槽位,**清不掉历史记录里和已同步到云端的条目**。这是密码管理器在 Windows 上的标准加固项,放置数据时同时设置:

- `CanIncludeInClipboardHistory`(DWORD = 0)——不进 Win+V 历史;
- `CanUploadToCloudClipboard`(DWORD = 0)——不上云;
- 或更通用的 `ExcludeClipboardContentFromMonitorProcessing`。

KeePass / Bitwarden 桌面端都做了这层处理。考虑到本项目的自动清空机制已经给了用户「剪贴板是安全的」的预期,缺这一层会让该预期不成立,建议补上。

#### M3. 坏头部的 KDF 参数上界仍然过宽,构成有效的本地 DoS
`src/header.rs:136-138`

```rust
if !(8..=1_048_576).contains(&header.m_cost_kib)   // 上限 1 GiB
    || !(1..=64).contains(&header.t_cost)          // 上限 64 轮
    || !(1..=64).contains(&header.p_cost)
```

口令加密的固有问题:KDF 参数在 AEAD 校验**之前**就必须使用,头部防篡改只能靠这个范围检查。但当前上界允许攻击者(或一个损坏的 `.pkk`)让解锁流程分配 **1 GiB 内存并跑 64 轮 Argon2**——UI 线程长时间假死,内存不足的机器直接 OOM(release 是 `panic = "abort"`,无提示闪退)。上界可以收紧一个数量级而不影响正常用途:

```rust
// 建议:按默认值(64 MiB / 3 / 4)留 4 倍余量封顶
if !(8..=262_144).contains(&header.m_cost_kib)
    || !(1..=12).contains(&header.t_cost)
    || !(1..=8).contains(&header.p_cost)
```

#### M4. `verify_master_password` 全量读文件且吞掉所有错误类型
`src/vault.rs:94-98`

```rust
pub fn verify_master_password(path: &Path, master_password: &str) -> bool {
    VaultFile::read(path)                       // 整个载荷(可能几 MB)读进内存
        .map(|file| unwrap_slot(...).is_ok())
        .unwrap_or(false)                       // IO 错误/文件损坏也报"密码不正确"
}
```

1. **性能**:只为解开 48 字节的密钥槽,却把整份载荷读进内存。应改用 `VaultFile::read_header` + 只读槽位字节。
2. **错误口径**:文件被删、被占、损坏时同样返回 `false`,UI 会提示「当前登录密码不正确」,误导排错方向。建议返回 `Result<bool>` 区分「读不了」与「密码错」——与 M1 的指纹校验联动时这个区分尤其重要。
3. 顺带:`change_master_password` 走「磁盘文件校验旧密码 + 内存 file 重包新槽」两条数据源,理论上存在 TOCTOU 窗口(解锁后文件被外部替换),M1 的保存前校验可一并覆盖。

#### M5. 空闲锁定检测失败方向是 fail-open
`src/win/idle.rs:11-31`

`GetLastInputInfo` 失败时 `idle_seconds()` 返回 `0`,即「用户刚刚还在操作」——自动锁定随之永不触发。安全相关的看门狗应当 fail-closed:拿不到输入信息时宁可误锁,不可不锁。建议失败时返回一个足够大的值(或单独的错误状态),并在文档中说明。

## 三、值得保持的做法(不建议动的)

1. **「先改内存再落盘 + dirty 标记」的坦诚设计**(`vault.rs:24-34`):不假装每次写盘都成功,用状态栏和拦截提示如实暴露中间态。M1 的指纹校验应当沿用同一套「如实告知」的交互哲学。
2. **导入在文档副本上完成、写盘成功才提交内存**(`vault.rs:552-660`):消除了整类「界面报失败、内存已导入、下次 save 静默写回」的 bug。
3. **URL 白名单放在可移植核心并有完整单测**(`src/url.rs`):`ShellExecuteW` 的协议分派风险被正确识别为安全判定。
4. **CSV 公式注入前缀只对自家文件还原**(`docs/security.md` §6.3):理解了带内转义与数据的不可区分性,这个判断很专业。
5. **恢复码字符纠正表**(`src/recovery.rs:36-42`):0→O、1→I、8→B、9→G 的映射安全——合法码的字母表本来不含这些数字,纠错不损失熵。
